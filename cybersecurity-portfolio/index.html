Detection Engineering

What it is. Turning raw logs into reliable alerts: designing detection use cases, writing and tuning rules, and making sure the underlying logging is complete and trustworthy.

Why it matters. Rules that fire constantly cause alert fatigue and hide real incidents. Rules that never fire give false comfort. Good detection engineering balances both, and depends on healthy log pipelines.

In my role

Detection tuning example Synthetic data

Reducing false positives is a trade-off, not a switch. This small simulation uses invented events (documentation IP ranges, made-up users) and illustrative pseudo-logic — not FortiSIEM syntax and not a rule from any employer. Move the threshold and see what changes.

RULE   console-login-failures   (illustrative pseudo-logic)
WHEN   eventName = ConsoleLogin            # AWS CloudTrail field
GROUP  BY sourceIPAddress, userName   WITHIN 10 minutes
IF     count(ConsoleLogin = "Failure") >= N
AND    (optional) a "Success" follows the failures
THEN   raise alert   # severity higher when a success follows
Synthetic login sequences and detection result
Source (synthetic)Sequence in windowScenarioAlert?Result
198.51.100.23 · user “alice”Mistyped password twice, then logged in
198.51.100.88 · user “carol”Forgot password, three tries, then success
203.0.113.45 · user “admin-demo”Repeated guessing, then a success
192.0.2.77 · user “bob”Failed guessing attempt, no success

F = failed login, S = successful login. “Scenario” labels are the example’s own ground truth. Lower thresholds catch more guessing but alert on ordinary typos; higher thresholds are quieter but can miss real attempts. Requiring a success reduces noise but ignores unsuccessful attacks, which may still deserve a low-priority look. Real tuning also uses allow-lists, user and asset context and business hours.

Security Testing Platform

A web platform for authorised security assessment of GenAI applications and APIs. Its defining feature is a scope-and-authorisation engine that refuses to test anything without a recorded grant, and it produces reproducible, framework-mapped findings.

  • Python
  • FastAPI
  • Next.js
  • PostgreSQL
  • Celery
Screenshot placeholder — save an image as assets/images/security-testing-platform.png
Read the case study
Problem / goal
Existing open-source AI red-teaming tools are strong, but the project’s own comparison found none that combine a hard authorisation boundary, tamper-evident evidence, cross-tool finding normalisation and statistically honest reporting in one workflow. The goal is defensible, reproducible findings for assessments that are explicitly authorised.
Objectives
  • Make authorisation a product feature: no grant, no scan.
  • Test AI applications, APIs and code with several engines and normalise their findings.
  • Report attack success rates with confidence intervals instead of single pass/fail results.
  • Keep evidence, reports and audit trails verifiable and access-controlled.
Architecture / workflow
  1. Browser → Next.js frontend
  2. FastAPI backend with PostgreSQL
  3. Redis and Celery workers run the security testing engines
  4. All outbound traffic passes the scope engine before reaching an authorised target
Technologies
  • Python 3.12
  • FastAPI
  • SQLAlchemy 2 (async)
  • Alembic
  • PostgreSQL
  • Redis
  • Celery
  • Next.js
  • React
  • TypeScript
  • Tailwind CSS
  • Docker Compose
  • pytest
  • Vitest
  • ruff
  • mypy
Implementation approach
  • A single scope-gated transport is the only place outbound requests are made, and a test keeps it that way.
  • API probes and AI probes; AI results are measured as attack success rates with Wilson confidence intervals against the probe’s own controls.
  • Static analysis, dependency, secrets and infrastructure-as-code engines, plus supply-chain checks.
  • Findings get stable fingerprints and risk scores; reports export as Markdown, HTML, PDF, JSON, SARIF and CSV.
  • A remediation board with a retest workflow, a CI gate with documented exit codes, and outbound integrations (chat, email, ticketing, pull-request checks).
Security considerations
  • A run without a recorded authorisation grant is refused.
  • Exclusions are checked before allowlists; DNS is re-resolved per request; private and cloud-metadata ranges are refused; redirects are never followed automatically.
  • Evidence is redacted before storage, content-addressed and hash-chained, and visible only to members of the owning organisation.
  • Argon2id passwords, optional TOTP two-factor authentication, server-side role-based access control, rate limiting, CSRF protection and server-side session revocation.
  • The AI assistant layer can draft and recommend but cannot start scans, grant authorisation or change findings. A high-impact exploitation tier requires a second, different engineer to approve.
Results & limitations
According to the repository’s README, the original multi-phase platform is complete and was verified end to end for its first release when run directly (not under Docker): an unauthorised run was refused, authorised runs completed, reports downloaded and the evidence chain verified. Limitations the README states itself: the Docker Compose path had not been exercised in the build environment, evidence is not encrypted at rest, and a limitations document records what the tool cannot detect and where false positives cluster.

The repository tracks built and deferred work phase by phase in a roadmap document. To add: your own next priorities

Automated IR Playbooks

Python incident response automation for Wazuh and Shuffle SOAR: three playbooks that turn detections into validated, auditable response actions.

  • Python
  • Wazuh
  • Shuffle SOAR
Screenshot placeholder — save an image as assets/images/automated-ir-playbooks.png
Read the case study
Problem / goal
Show how a SOC can turn detections into validated, auditable response actions while remaining runnable offline in simulated mode.
Objectives
  • Cover three common scenarios: brute force, malware/IOC, and account compromise.
  • Make every containment action support --dry-run.
  • Keep integrations simulated by default and label simulated results clearly.
  • Commit no credentials.
Architecture / workflow
  1. Wazuh alert
  2. Shuffle SOAR workflow
  3. Python playbook
  4. Investigation / enrichment
  5. Automated containment
  6. Ticket / incident
  7. SOC notification
Technologies
  • Python
  • Wazuh SIEM & Active Response
  • Shuffle SOAR
  • pytest
  • YAML configuration
Implementation approach
  • Brute force: validates repeated failed logins, blocks the source IP via Wazuh Active Response, collects authentication evidence, creates an incident and notifies the SOC.
  • Malware/IOC: enriches host and IOC data through Shuffle, isolates the host, collects evidence, creates an incident.
  • Account compromise: protects privileged and service accounts, disables normal accounts, creates an incident.
  • Ticketing and notification adapters share a stable result contract so real providers can be swapped in.
Security considerations
IR_EXECUTE_REAL_ACTIONS=false is the default; protected accounts are respected; upstream data is validated; the repository documents TLS, secret management, least-privilege Active Response, audit logging and rollback approval.
Results & limitations
The repository includes tests for all three playbooks, invalid input, dry-run behaviour, incident creation and protected-account handling. Integrations are simulated by default: this is a demonstration framework, not a production deployment without provider-specific security review.
Future improvements
Provider-backed adapters with retries and timeouts, signed webhook verification, persistent audit storage, IOC reputation providers, approval gates for high-impact actions, and CI security/test gates (from the project’s own roadmap).

Future improvements
Secured remote backend with locking, environment claims in OIDC trust, and a separate protected deployment workflow with approval (from the project’s own notes).
