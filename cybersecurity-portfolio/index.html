About

Security operations, connected to engineering

Alerts only become security when someone can explain what they mean, what to do next, and how to stop the same noise tomorrow.

I’m a cybersecurity analyst with hands-on SOC experience across threat detection, alert triage, incident response, and vulnerability management in cloud and hybrid environments.

My work covers SIEMSecurity Information and Event Management: a platform that collects logs from many systems, correlates them and raises alerts. detection engineering, endpoint and edge monitoring with CrowdStrike Falcon and Cloudflare, and log correlation across AWS CloudTrail, CloudWatch, Kubernetes, and container workloads. I take incidents from initial triage through to post-incident review, then feed what I learn back into detection tuning and reporting.

I have working knowledge of ISO 27001, NIST CSF, PCI DSS, and SOC 2.

Detect

Design and tune detection rules, define logging standards, and watch the log pipeline itself — ingestion gaps, outages and clock drift — because a detection is only as good as the data behind it.

Investigate

Triage alerts from endpoint, edge, cloud and container sources, correlate events across them, and carry incidents through containment support to a post-incident review.

Improve

Maintain playbooks, run tabletop exercises, report on detection coverage and alert quality, and work with engineering and infrastructure teams so findings become fixes.

What it is. Continuous monitoring of alerts and events to spot possible threats, decide which are real, and escalate the ones that matter.

Detection Engineering

What it is. Turning raw logs into reliable alerts: designing detection use cases, writing and tuning rules, and making sure the underlying logging is complete and trustworthy.

Why it matters. Rules that fire constantly cause alert fatigue and hide real incidents. Rules that never fire give false comfort. Good detection engineering balances both, and depends on healthy log pipelines.

In my role

  • Develop and tune FortiSIEM detection rules to reduce false positives and improve actionable alert quality across AWS CloudTrail, CloudWatch, Kubernetes and container workloads.
  • Define and enforce logging standards; monitor ingestion gaps, pipeline outages and NTP driftNTP drift means a system’s clock has wandered from the reference time source. Timestamps then disagree between systems, which breaks event correlation and incident timelines..
  • Track detection coverage, alert quality, false-positive rates and response timelines.

Practices

  • Detection use-case design
  • False-positive reduction
  • Alert-quality optimization
  • Logging standards and ingestion monitoring

Cloud & Endpoint Security

What it is. Monitoring the platforms workloads actually run on — cloud accounts, containers and endpoints — using the audit trails and telemetry they produce.

Why it matters. In cloud environments most attacker actions are API calls and configuration changes. If those aren’t logged and correlated with endpoint and edge signals, they are invisible.

In my role

  • Correlate AWS CloudTrail, CloudWatch, Kubernetes and container events alongside CrowdStrike Falcon and Cloudflare alerts.

Security incident lifecycle

Six stages from raw logs to lessons learned. Select a stage to see its purpose, which sources feed it, and where my own work sits.

General practice

Purpose. Gather security-relevant events from endpoints, cloud accounts, containers and edge services into one place, with consistent fields and trustworthy timestamps.

Why it matters. Everything downstream depends on it. If a source stops sending logs or its clock drifts, detections silently fail and timelines can’t be trusted.

Contributors. Cloud logs (CloudTrail, CloudWatch, Kubernetes) and endpoint telemetry feed the pipeline; the SIEM ingests and normalises.

My experience
  • Define and enforce logging standards across application, infrastructure and audit environments.
  • Monitor logging pipelines for ingestion gaps, outages and NTP drift.
General practice

Purpose. Link events from different sources into a single story — for example an unusual cloud API call, followed by an endpoint alert, from the same user.

Why it matters. Single events are often ambiguous; correlated events show intent and reduce false positives.

Contributors. The SIEM’s correlation rules do the heavy lifting, using cloud logs and endpoint detections as inputs.

My experience

Why it matters. The commit is the cheapest place to catch a problem: the author still has full context, and nothing has shipped.

What happens. Scanners look for credentials, tokens and keys accidentally committed to a repository.

Why it matters. A leaked secret is usable immediately and lives on in git history. Remediation means revoking and rotating it, not just deleting the line.

General practice

What happens. Policy decides whether a build may proceed — for example blocking on confirmed critical findings, while lower-severity issues create tracked tickets.

Why it matters. Gates turn scan output into enforceable policy. Set too strict they get bypassed; too loose they protect nothing.

General practice

What happens. Artifacts that pass the gates are built and deployed. Runtime monitoring then takes over — which is where the SOC’s cloud and container telemetry comes in.

Why it matters. Pre-deployment checks reduce risk but never remove it; detection and response remain necessary.

Detection tuning example Synthetic data

Reducing false positives is a trade-off, not a switch. This small simulation uses invented events (documentation IP ranges, made-up users) and illustrative pseudo-logic — not FortiSIEM syntax and not a rule from any employer. Move the threshold and see what changes.

RULE   console-login-failures   (illustrative pseudo-logic)
WHEN   eventName = ConsoleLogin            # AWS CloudTrail field
GROUP  BY sourceIPAddress, userName   WITHIN 10 minutes
IF     count(ConsoleLogin = "Failure") >= N
AND    (optional) a "Success" follows the failures
THEN   raise alert   # severity higher when a success follows
Synthetic login sequences and detection result
Source (synthetic)Sequence in windowScenarioAlert?Result
198.51.100.23 · user “alice”Mistyped password twice, then logged in
198.51.100.88 · user “carol”Forgot password, three tries, then success
203.0.113.45 · user “admin-demo”Repeated guessing, then a success
192.0.2.77 · user “bob”Failed guessing attempt, no success

F = failed login, S = successful login. “Scenario” labels are the example’s own ground truth. Lower thresholds catch more guessing but alert on ordinary typos; higher thresholds are quieter but can miss real attempts. Requiring a success reduces noise but ignores unsuccessful attacks, which may still deserve a low-priority look. Real tuning also uses allow-lists, user and asset context and business hours.
